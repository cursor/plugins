# 基于原始 pstack 的宿主适配计划

## 目标与边界

以 `cursor/plugins` 的 pstack 为来源，保留技能名字、完整正文、参考文件和业务流程，让 Codex 与 Claude Code 可以通过 `npx skills add` 安装，再通过 `setup-pstack` 完成宿主配置。适配覆盖普通技能、两个原始 agent，以及 benny 的分类、复现和修复流程。

2026-10-14 用户已授权基于 upstream 开始实施。实施和隔离测试在独立工作区进行，不安装到用户环境，不启用真实自动化。实施内容以 `upstream` 为来源，新建独立 PR 分支，向 `main` 提 PR；不修改 `main`、不重写原 PR 分支历史。旧 PR 的取舍在新 PR 中说明，不自动关闭。

无需继承旧移植的五宿主生成器、Python 安装 CLI 或 51 份发布副本。旧 CLI、会话查看器和运行记录工具的保留、移除及升级影响必须先列明，不能随目录替换静默删除。

## 安装与文件布局

先验证原始 `skills/` 可以被真实 skills CLI 发现和安装。不要先引入发布生成器。全量安装只选择普通技能；不能把 benny 的嵌套技能误当成普通入口。

安装后的技能目录只存发布内容。项目配置和运行状态写到调用项目；全局安装时也不得把项目状态写进全局技能目录。路径以宿主提供的实际 skill location 为起点，禁止硬编码插件缓存或本地源码 checkout。

已确认 `skills/poteto-mode/scripts/bootstrap.ts` 会在自身目录执行 `bun install --frozen-lockfile`，生成 `node_modules` 和安装标记。适配必须检查 bootstrap、模块解析和全部调用者，将依赖安装与缓存转到调用项目的私有运行目录；具体路径待实现确定。保留原锁文件约束，确认第一次安装、重复执行、锁文件变化和脱离源码运行均正确，运行前后比较已安装技能的哈希。不能只改 cwd 导致依赖无法解析。

公共文件只保留一份。若真实安装证明无法携带目录外依赖，才新增一个公共支持技能，用于保存两种宿主的指令、原始 agent 正文及 benny 源文件。这个名称和布局在确定前均为待确认，不把旧移植的 `pstack-runtime` 误称为原始插件已有技能。

若采用公共支持技能，全量安装会包含它；单技能安装必须显式选择它，或在调用前显示确定的补装命令。`skills add` 不被假设为自动解析依赖。预检必须处理项目版本覆盖全局版本、旧版公共文件和混装来源；不以当前源码目录存在作为安装完整证据。

不压缩正文为一行、不改成运行时下载完整仓库、不用跨安装目录的未验证软链来缩小 diff。统计文件数、总字节、重复公共文件及相对 `main` 的差异，把实际减少和来源替换产生的差异分开报告。

## 宿主适配

### 委托与模型

保留完整任务要求，替换 Cursor 的委托参数、模型 slug、等待和恢复方式。Codex 与 CC 分别使用其当前官方接口，执行前检查当前会话是否提供对应能力。

模型只取本机可用且已确认的名字，不把 Cursor 的 Grok 名称传给 Codex 或 CC。不承诺跨厂商模型对比；只能使用同一厂商模型时，保留候选数量和不同评审角度，并报告能力差异。没有原生委托时，报告该流程不能按委托方式运行，不能把主线程多次自问当成原生委托验证。

只读 persona 与实际权限限制分别说明。保留 Bash 或 MCP 写工具的 reviewer 不能被声称具有完整只读隔离。云端执行缺失时，明确实际执行位置；本地 worktree 不等于云端环境。

### setup 与 agent 注册

`setup-pstack` 从已安装内容读取两份原始 agent 正文，为当前宿主配置原生命名 agent。Codex 的目标为 `.codex/agents/` 配置；CC 的目标为 `.claude/agents/` 定义。具体字段、配置发现范围及是否要重启，以实施时官方文档和实际会话验证为准。

将 Cursor 的 `~/.cursor/rules/pstack-models.mdc` 改为目标宿主可加载的模型及常驻指令配置。优先使用宿主现有格式，不额外建立一套未经需要证明的配置系统。已有用户内容保留，只更新确属 pstack 管理的部分；有同名用户 agent 时比较正文并报告冲突，不静默覆盖。

setup 应可重复执行、识别版本变化，并保留用户模型选择。若写文件是模型按说明执行，文档必须如实说明；不能把提示词描述当成已经实现的幂等脚本或注册器。写完回读目标文件，并在新会话确认 agent 名称能被实际调用。

setup 同时负责首次配置和后续 agent 更新。更新 skills 不会自动更新已复制到项目中的 agent；使用文档应明确要求“更新 skills → 重跑 setup → 在新会话验证 agents”。上游管理的 agent 正文和宿主适配规则随版本更新，用户的模型选择、权限配置和个人修改应保留。

记录实际安装来源提交和上次成功写入的各 agent 文件哈希，记录位置及字段在实施时确定。来源提交不能删除，否则无法追溯配置来源；上次写入哈希不能删除，否则无法区分旧版管理文件与用户修改。再次运行时逐文件比较已安装版本、当前项目文件和上次写入记录：

- 已安装版本和项目文件均未变：检查配置，不重复改写。
- 已安装版本变化、项目文件仍与上次写入哈希一致：更新上游管理内容，保留用户配置，并回读后更新记录。
- 项目文件被用户修改：展示本地改动及拟更新内容，处理冲突后再写入，不静默覆盖；已安装版本未变时也保留本地修改。
- 没有上次写入记录或存在同名用户 agent：先比较并确认归属，不能直接认定文件由 pstack 管理。

如宿主支持 agent 配置直接引用已安装正文，可在验证引用能力、更新行为和路径稳定性后减少复制；未验证前不依赖跨目录引用。上述更新规则属于待实现要求，不能据此声称已有更新脚本。

### Cursor 专用技能

逐文件列出 Cursor 专用假设，至少包含 `setup-pstack`、`arena`、`swarm`、`poteto-mode` 和 `make-bot-ui`。普通原则技能不作无关改写。

`make-bot-ui` 依赖 Cursor 的 `update_state`、webhook routine 和 sender key，不能仅替换产品名。保留该入口并说明具体依赖；如 Codex、CC 没有等价原生接口，定义可执行的目标宿主方案及其工具条件，或明确标为尚未适配，不能把它从验收清单中排除后宣称全部适配。

## benny 自动化

源流程为：新 Slack 顶层报告触发分类；复现流程等待原线程里受信任的分类标记，再检查已有修复、复现、验证并按条件准备草稿 PR。保留源频道和线程坐标，子 agent 不得收到 Slack 凭证或发布权限。

宿主适配分别处理三件事：流程指令、外部工具、触发器。Slack 读取与原线程回复、tracker 去重与更新、附件下载、目标应用控制以及草稿 PR 创建，都必须有实际可用的工具；调度器本身不能代替这些工具。

Codex 优先核对其当前自动化能力，CC 优先核对持久化定时任务或 Routines。对 Slack 事件触发，先确认当前账户与工具能否直接支持。不支持时采用定时读取并去重的可执行方案，明确它是轮询且依赖 runner 的运行条件。不得创建一个只会显示提示词、拿不到事件或频道内容的“自动化”。

去重标识由已存在的 Slack 频道和源线程时间戳组成；恢复和重试不得重复回复或新建 ticket。分类与复现之间保留可信作者及标记检查。配置和去重状态的具体存储路径在目录设计确定后记录，不新增用户可调档位。凭证从连接器、宿主已有凭证机制或环境读取，不写入技能、提交或日志。

setup 将完整 benny pack 合并到目标仓库的项目目录，目标路径实施时确定并记录。保留目标独有文件；已修改的源管理文件先比较并合并，不覆盖用户内容。用户配置、routing map、feature map 和凭证放在 pack 外。运行 prompt 直接读取同一目标仓库中已提交的操作指令及配置路径，禁止引用插件缓存或全局安装路径。启用前核对提交、文件和配置，并在目标项目新会话验证 `how`、`why`、`tdd`、`unslop` 及所需原则技能；当前会话或全局可见的技能不能代替项目依赖验收。

提供配置、回读和测试步骤，不在安装普通技能时自动启用 benny。真实自动化、Slack 消息和 tracker 写入需要用户明确指定测试目标并授权；测试使用专用频道和项目。连接缺失时可以验证模拟事件，但必须标记真实外部运行未验证，不能用手动执行代替自动触发验收。
