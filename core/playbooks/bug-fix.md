### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

A gate line belongs to the step it sits under and runs at that point, not at the end of the list. Copy it with its step. A step is not done while one of its applicable gates is open. A gate that does not apply stays in the list with `skip: <reason>`.

**Run record.** Start one before step 1 with `scripts/run-record.py`, in this skill's directory: `python3 <that path> init --route bug-fix --task "<the request>"`. Below, `rr` stands for `python3 <that path>`. Each step names what it records. `rr check` refuses completion when evidence is missing, or was taken on code that changed after it. It cannot make evidence true, so the reply still shows the output. With no Python on the host, keep the same entries by hand in `.pstack/runs/<id>.md` and say the check did not run.

Include `--run <printed-id>` in `rr` for every command. Record `rr phase <name> --start` before each named phase's work, including cleanup, review, and verification. Record transitions with `--from <source> --reason "<why>"` on the destination's start. During root-cause, record `root-cause/how` and `root-cause/why` separately with their host agent ids, followed by `root-cause/confirm` for the parent's runtime confirmation. During planning, record `plan/architect-a`, `plan/architect-b`, and `plan/architect-c`; skip C with a reason when approval was not requested. Close applicable children before their parent. Follow `references/session-tracking.md` for parallel joins, evidence links, and retries. A failed verification gets `rr phase verify --fail "<reason>"` before `rr phase root-cause --start --from verify --reason "<why the mechanism needs rechecking>"`. Mark verification done only after it passes.

1. Reproduce it yourself on the matching surface via the control skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
   - **Gate, before the first edit.** Work from a git worktree off main, per Opening a PR's **Worktree** rule, and name the verification driver: the project's control skill, or one generated with **create-verification-skill**. The worktree rule cannot wait for Opening a PR, because by then the edits exist. A run record started before the worktree existed moves into it before any evidence: from inside the worktree, `rr workspace --path .`. `rr` records only from the run's workspace.
   - **Gate, before step 3.** Capture the repro as an executable check and watch it fail for the bug's reason. Use a regression test per the **tdd** skill when the bug has a cheap local test path. Otherwise use a script or driver run, and save its full output to a file under `.pstack/runs/<run-id>/` or outside the working tree. `rr` refuses an output anywhere else in the tree. An import error or a missing attribute is not a failing repro, so read the failure before you keep it. Commit the check on its own. That commit is the failing-test commit that step 4 freezes. Record it with `rr baseline --harness <paths> --command "<cmd>" --output <file>`, then `rr evidence --kind repro --result fail --output <file>`, then `rr phase reproduce --done`. If the check will not fail for the bug's reason, stop and report that unmet condition instead of continuing to a fix.
2. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with `how` over the affected subsystem and the **why** skill for regression history. Record each result with `rr ground add --skill how|why --scope <paths> --output <file>`, so a later step can reuse it. Their reports seed hypotheses. They do not confirm one. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Drive a long or stubborn hunt with the host's `/loop` command. Confirm the surviving *mechanism* with runtime evidence before step 3, record that as `rr phase root-cause/confirm --done`, then `rr phase root-cause --done`. `rr check` refuses a root cause closed without the confirmation.
   - **Gate, when two or more fixes that share one premise have failed the same gate.** Read **principle-attack-the-premise**. Write the premise and its census before the next attempt. A census that refutes the premise sends you back to the hypotheses. Do not rerun the same census without new evidence.
3. Plan the fix.
   - **Gate, before any implementation fan-out.** Write the throughput checkpoint (Feature step 3).
   If the fix crosses a function boundary, `architect` first, as its caller. Architect stops after Phase C and returns the synthesized design. The one implementation delegate below is its Phase D. Scale the fan-out to the
   blast radius: a fix confined to one module takes design sketches compared on shape, not a bakeoff
   of working candidates. Escalate to a full `arena` of running implementations only when the
   candidates differ on something no sketch can settle, and say what that was. `rr phase plan --done`, or `--skip "<reason>"` for a fix inside one function. Delegate implementation to one subagent using your configured bug-fix model (default the `fast` class) with a specific scope: the sketch as its contract when Architect ran, the file paths, the failing check from step 1, and the success criterion. Record it with `rr delegate --role <role> --model <model> --job implement`, then `rr phase implement --done`. On a host with no delegation (Tier 0 in `runtime/capabilities.md`), you implement it yourself and record `rr phase implement --done --note "parent: <the limitation>"`. A diff that violates the design sends you back to Architect Phase B, not to a patch.
   - **Gate, before review.** Strip code slop from the diff, then run the **no-comments** skill. Then review the diff yourself. `rr phase cleanup --done`.
   - **Gate, before commit, when the shipped fix is a synthesis no single candidate built, or it changes durable state, retries or failure handling.** Run **interrogate** on the final diff, with an `operator` reviewer on the panel. The operator's question is what a crash between every pair of lines does to a delivery. Interrogate returns a verdict and edits nothing. Record it with `rr evidence --kind review`, and each Act-on finding you accept with `rr finding add`. Each accepted finding goes back to a fresh implementation delegate, and the code it changes passes this step's gates again. Close it with `rr finding resolve --status fixed|dismissed --reason "<why>"`. An Act-on finding you do not fix stays in the reply as an open blocker with its reason, and the reply does not claim success. `rr phase review --done`, or `--skip "<reason>"` when the trigger does not apply.
4. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
   The repro and its harness are frozen at the failing-test commit. Verify against them exactly as committed there. If the fix has to change the harness, run the original harness as well and report both results: a scenario that passes only on a harness edited in the fix commit has not passed. Record each run with `rr evidence --kind verify --result <result> --output <file>`, adding `--harness original` for the frozen harness when the fix changed it, then `rr phase verify --done`.
   A verification is stale once code or harness changes after it. A later edit (an accepted review finding, a no-comments fix, the Opening a PR slop pass) sends you back to this step before commit or PR. A failed or inconclusive result sends you back to step 2.
5. Stage the commits so the failing-check commit from step 1 lands before the fix in git history. This step arranges history. It does not write the failing check for the first time. See the **tdd** skill for the failing-test-first cadence. A rebase that changes no content keeps step 4 current.
   This is the canonical **sequence-verifiable-units** principle skill, the failing test first and the fix on top.
   - **Gate, before commit.** Write commit messages with **technical-writing**. Then `rr phase commits --done`.
6. Run **Opening a PR**. Run `rr check --through commits` before you create the PR, and do not create it while the check reports a problem. An edit it makes to code or harness sends you back to step 4. Then `rr phase open-pr --done`, and `rr check` before the reply.

Investigation fans out `how` + `why` as parallel subagents. You run both skills yourself and spawn their explorers and investigators; you do not hand a delegate the whole skill (see `runtime/delegation.md`, Reaching a routed skill).

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim: every line, summaries included, from the same harness. If it is too long, give the file path instead of trimming it.

- **Gate, before sending the reply.** Apply **unslop**.

End the reply with an audit block, one line each:
- the checklist, every step and gate marked done or `skip: <reason>`;
- the final `rr check` output, or the reason it did not run;
- who wrote the implementation: the delegate and its model, or `parent` and the reason;
- the principles that shaped a decision, each with the choice it changed, citing only leaves you read this session;
- every assumption the run made about the world outside the repo (deployment, provider behavior, scale), each marked `answered by the user` or `assumed`;
- the tier the fan-outs ran at, and every capability that degraded.
