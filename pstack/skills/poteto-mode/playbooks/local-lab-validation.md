### Local lab validation

**You own the lab verdict. CI is a prerequisite, not the verdict.** Use this playbook for an explicit local-lab request, or when a change crosses deployed services, runtime protocols, durable ownership, upgrade or migration paths, hardware adapters, physical actuation, or production-readiness gates.

Run it against the exact pushed PR head after prerequisite CI and preview artifacts complete. Run it before calling the work production-ready or starting **Shipping**. An open PR may carry a pending or blocked verdict. A lab pass never authorizes deployment, rollout enablement, or release promotion.

1. **Classify the lab risk.** Name every affected deployable, runtime seam, state owner, upgrade combination, hardware family, and credible user failure. Keep ordinary single-process work on its matching local control surface; do not send it to the lab because many packages compile.
2. **Find the project's controls.** Read repository instructions, `CONTEXT.md` when present, lab runbooks, release rules, and project-local verification skills. Search for existing lab, integration, smoke, replay, simulator, and hardware-test entry points. Use the existing control. If no control can prove the affected seam, build the smallest rerunnable verifier first. A hand-entered command sequence is not a reusable feedback loop.
3. **Freeze the candidate.** Shape and commit the candidate first. Open or use its PR, push the exact head, and wait for prerequisite CI and preview artifacts. Record the repository, branch, commit SHA, build identity, service versions, migrations, feature flags, lab environment, and redacted device identities. A later code, configuration, migration, or build change invalidates the affected scenarios.
4. **Write the scenario matrix before touching the lab.** Each row names the scenario, affected boundary, stimulus, expected invariant, authoritative observations, cleanup, and required ladder rung. Include the changed path, its normal path, and the relevant failure or recovery path. Stateful changes also cover retry, restart, stale authority, or duplicate delivery when applicable. Upgrade-sensitive changes cover the supported version mix.
5. **Climb the available lab ladder in order.** Run focused automated and loopback proof first. Then run isolated real-service proof, an adapter mock or replay, read-only live hardware proof, and supervised physical actuation only when the change requires each rung. A higher rung does not replace a failed lower rung. Use the repository's release verification after the lab when the changed product has one.
6. **Keep the lab isolated and physical actions supervised.** Use designated lab tenants, fixtures, and devices. Never use customer data or customer-owned hardware. If a lab device connects to a production service, follow the project's scoped lab policy and prove that the lab identity cannot reach customer work. Require the user's explicit authorization before the first real motion, heater, actuator, print, or comparable hardware command unless the user already authorized that exact run. Use the product's safety path and its target binding, lock, confirmation, rollout gate, and single-use arm. Never bypass a refused safety gate with raw commands. Keep the documented stop control available. Stop on unexpected state, motion, contact, sound, heat, connectivity loss, or indeterminate identity.
7. **Observe every authority in the changed path.** Read the producer, transport, authoritative state owner, downstream projection, and physical result when one exists. Do not treat request success, queue acceptance, socket acknowledgment, or command acknowledgment as completion. Correlate observations with stable identifiers from the frozen candidate and scenario.
8. **Prove cleanup.** Remove test work and temporary fixtures. Revoke one-shot arms. Restore flags and configuration. Confirm that no lab job, lock, lease, queue item, outbox row, process, or unsafe hardware state remains. A run that cannot return the lab to a known safe state is not a pass.
9. **Write a Lab Validation Receipt.** Record the frozen candidate, scope, environment, scenario results, redacted evidence references, safety decisions, cleanup result, operator, time, and one verdict. `PASS` means every required scenario passed. `PASS+NOTES` means every required scenario passed and the notes do not reduce coverage or weaken an invariant. `FAIL` means a required scenario failed. `BLOCKED` means a required scenario or rung did not run, the candidate became stale, cleanup is unknown or unsafe, or required evidence cannot be retained. List every skipped or unreachable surface and its effect on readiness. Follow the repository's evidence storage policy. Otherwise keep detailed artifacts private and post the concise receipt to the PR.
10. **Gate the claim.** Only `PASS` and `PASS+NOTES` support a production-ready claim. `FAIL` and `BLOCKED` stop Shipping. Missing lab access is `BLOCKED`, not an inferred pass. Lab success does not grant merge, deploy, promotion, or hardware rollout authority.

**Reply:** the exact candidate, the scenario matrix and results, the receipt verdict, evidence references, cleanup proof, gaps, and what remains before production.
